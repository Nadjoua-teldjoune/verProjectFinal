Understanding Architectural Tactics

Architectural tactics are recurring solutions to specific problems in software system design. They represent the "building blocks" that software architects use to address quality requirements such as scalability, resilience, security, and performance.

This interactive guide explains in detail each tactic identified in your UML diagrams, with concrete examples, use cases, and implementation best practices.

Monitoring

Ping Echo Tactic

This tactic involves sending a "ping" message to a component to verify its availability and waiting for a "pong" response. It's a fundamental monitoring mechanism for distributed systems.

Interaction pattern: A → ping() → B → pong() → A
Typical frequency: Every 30 seconds to 5 minutes depending on criticality
Why use this tactic?

In modern architectures (microservices, APIs, cloud), rapid failure detection is crucial. This tactic enables:

  • Proactive detection of failing components
  • Network latency monitoring between services
  • Integration with alerting systems (like Prometheus)

It's particularly important for systems where response time is critical (fintech, online gaming, IoT).

Typical Implementation

1. Implement a `/health` or `/ping` endpoint on each service

2. Configure a monitoring service to regularly poll these endpoints

3. Define alert thresholds (e.g., 3 consecutive missed pings)

4. Integrate with your logging and alerting system

Advantages

  • Simple to implement
  • Low overhead
  • Fast failure detection
  • Standardized (HTTP health checks)

Limitations

  • Doesn't detect all types of failures
  • Can generate false positives (network congestion)
  • Requires fine-tuning of timeouts
Further reading: Designing Data-Intensive Applications, Health Check Pattern
Resilience

Maintain Multiple Copies

Data duplication across multiple nodes to ensure availability and durability, even in case of hardware failure.

Replication pattern: Master → replicate(data) → Replica1, Replica2
Common strategies: Synchronous (strong consistency) vs Asynchronous (eventual consistency)
Why is this tactic essential?

Modern distributed systems must withstand failures. This tactic provides:

  • High availability (zero-downtime upgrades)
  • Disaster recovery
  • Load balancing (reads on replicas)
  • Compliance with regulations (GDPR on durability)

Implementation

Databases: Native replication (MySQL, PostgreSQL, MongoDB)

Distributed storage: RAFT consensus (etcd, Consul)

Cloud: Multi-AZ deployments (AWS), GCP Regional Disks

Key factors: Replication factor choice (typically 3x), quorum strategy

Advantages

  • Increased resilience
  • Better performance (local reads)
  • Horizontal scalability
  • Geo-distribution compatibility

Challenges

  • Synchronization complexity
  • Multiplied storage cost
  • Consistency trade-offs (CAP theorem)
  • Network overhead
References: DSDM Agile Project Framework, RAFT Consensus
Confidentiality

Maintain Data Confidentiality

Protection of sensitive data through encryption during transfer (TLS) and at rest (encryption-at-rest).

Typical flow: Client → encrypt(data) → API → decrypt → DB (encrypted)
Common algorithms: AES-256 (symmetric), RSA (asymmetric), ECC
Security challenges

In a context of growing cyber threats and strict regulations:

  • Protection against data leaks
  • Compliance (GDPR, HIPAA, PCI-DSS)
  • User trust (reputation management)
  • Defense in depth

Secure Implementation

In transit: TLS 1.2+ (HTTPS), Perfect Forward Secrecy

At rest: TDE (Transparent Data Encryption), Client-side encryption

Key management: HSMs, AWS KMS, Hashicorp Vault

Best practices: Regular rotation, role separation, audit logs

Benefits

  • Protection against attacks
  • Customer trust
  • Legal compliance
  • Reduced financial risk

Considerations

  • Performance overhead
  • Management complexity
  • Solution costs
  • Key loss risk
Learn more: Applied Cryptography, OWASP Top 10
Authorization

Authorize Users

Access control based on roles (RBAC) or attributes (ABAC) to restrict user actions.

Workflow: User → requestAccess → AuthZ → Policy Engine → (allow/deny)
Standards: OAuth2 scopes, JWT claims, Open Policy Agent (OPA)
Need for access control

To prevent:

  • Unauthorized access (data breaches)
  • Privilege escalation
  • Violations of separation of duties (SoD)
  • Non-compliance with internal policies

Implementation Models

RBAC: Roles → Permissions (admin, user, auditor)

ABAC: Policies based on attributes (time, location, device)

Solutions: Keycloak, Auth0, AWS IAM, Casbin

Patterns: Separate Policy Decision Point (PDP) from Policy Enforcement Point (PEP)

Strengths

  • Fine granularity
  • Auditability
  • Centralized rules
  • Adaptability to needs

Complexities

  • Permission management
  • Check performance
  • Combination explosion (ABAC)
  • Policy maintenance
Resources: Auth0 Authorization, NIST ABAC Guide
Authentication

One-Time Password

Two-factor authentication (2FA) mechanism using a unique temporary code.

Flow: User → login → SMS/Email/App OTP → validation → session
Technologies: TOTP (Time-based), HOTP (HMAC-based), SMS, Push notifications
Security reinforcement

Complements passwords (often weak/reused) by adding:

  • Second knowledge factor (OTP)
  • Protection against phishing
  • Reduced credential stuffing risk
  • Compliance with standards (PSD2 SCA)

Implementation Options

Self-hosted: FreeOTP, Google Authenticator libs

SaaS: Twilio Verify, Authy, Duo Security

Standards: RFC 6238 (TOTP), RFC 4226 (HOTP)

Alternatives: WebAuthn (FIDO2), Push-based 2FA

Advantages

  • High security at moderate cost
  • Wide adoption/usability
  • Broad compatibility
  • Device independence (SMS)

Challenges

  • User experience (friction)
  • SMS cost (possible fraud)
  • Device dependency
  • SIM swapping vulnerability
Learn more: OWASP 2FA, RFC 6238 (TOTP)
Composite Security

ID/Password + Confidentiality

Combines username/password authentication with data encryption to guarantee both user identity and information confidentiality.

Workflow:
1️ User → submitCredentials → Authenticator
2️ Authenticator → verifyCredentials
3️ Data → encrypt → transmit → decrypt
Standards: HTTPS, JWT, AES, TLS, bcrypt
Why this combination?

It enables:

  • Reliable user authentication
  • Protection of exchanged sensitive data
  • End-to-end security

Typical Implementation

Authentication: Login with ID/Password securely stored (hash/salt)

Confidentiality: Data encrypted before sending (AES-256, TLS)

Solutions: OpenID Connect + HTTPS + WebCrypto API

Examples: Banking portal login, medical EHR, etc.

Strengths

  • Complete security: access + content
  • Standardized deployment
  • Suited for web/cloud systems

Limitations

  • Risk if weak password
  • Key/encryption management complexity
  • Performance under load
References: CIO Security Trends, Distributed Patterns
